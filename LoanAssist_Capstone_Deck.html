Loan Eligibility Assistant — Problem Statement

Customers cannot easily read lending policy — and a generic LLM cannot be trusted to read it for them.
  • Eligibility depends on many interacting rules — age, income, employment vintage, CIBIL score, obligations, tenure — and they differ for every loan product.
  • Policy documents are written for underwriters, not applicants; customers cannot map their own situation onto them.
  • FAQ and keyword search return documents, not answers to "does this apply to me?"
  • A generic LLM will invent thresholds — a confidently wrong income cut-off is a compliance problem, not a UX one.
  • Call centres absorb the gap, so routine eligibility questions consume agent time.
Problem statement

Build a conversational GenAI assistant that answers eligibility questions with preliminary guidance grounded in approved lending policy — citing the exact rule behind every answer.

Explicitly not

A final loan approval, sanction, or underwriting decision engine. Output is pre-qualification only, subject to verification and full credit assessment.

01

Speaker notes — about 60 seconds

Start with the customer. Someone thinking about a personal loan has one question: "will I qualify?" Answering it properly means checking age, income, how long they have been employed, their CIBIL score, existing EMIs and the tenure they want — and every one of those thresholds changes depending on whether it is a home loan, an auto loan or a loan against property.

That information does exist, in the lending policy. But policy is written for underwriters. A customer reading it cannot tell which of eleven sections applies to them. Search does not fix this, because search returns documents and the customer asked a question about themselves.

The obvious shortcut is to hand the question to ChatGPT — and that is exactly the trap. A general model will happily state an income threshold. It will sound authoritative and it will be made up. In lending, a hallucinated threshold is a compliance and mis-selling issue.

So the problem I set myself was narrower and harder: ground every answer in the approved policy, and make the system cite the rule it used. Be clear about the boundary — this is pre-qualification guidance, never an approval decision.

02

Speaker notes — about 60 seconds

Scope first, because scope is what keeps a GenAI project honest. The system holds a real conversation, retrieves the policy clauses that apply, generates an answer grounded in them, runs it through guardrails, and returns a structured decision with citations. It runs locally, in containers, with metrics.

What it does not do matters just as much. It does not approve loans. It does not touch a core banking system or pull a real CIBIL score. It does not deploy to a cloud. And I want to be precise about one thing — the API key header is sent by the UI but it is not yet enforced in the API code, so this is not an authenticated service. I have listed that as future scope rather than claiming it.

The single design decision behind everything is on the flow at the right: the model is never asked what the eligibility rules are. It is handed the retrieved rules and asked to apply them. That turns an open-ended generation problem into a constrained reasoning problem — which is what makes the output defensible.

03

Speaker notes — about 90 seconds

Read the top band left to right. Streamlit is the UI and runs on the host; everything else is containerised. It calls FastAPI. FastAPI is here because it is async, and because Pydantic gives me a typed response contract — decision, citations, confidence and refusal are schema fields, so a refusal is a normal 200 response with refused: true, never a 500.

Second row is the grounding. The question goes into ChromaDB. Chroma because the corpus is small and the index can be embedded in the API process — zero extra infrastructure for a lab, and the interface is the same one a managed vector database would expose later. Ingestion splits the policy by clause rather than by fixed window, so one chunk is one citable rule with a stable Rule ID. Embeddings are all-MiniLM-L6-v2 running locally as ONNX — no embedding API calls, no cost, no data leaving the machine.

Third row generates. LiteLLM is the gateway because it decouples my code from the provider — the API only ever speaks OpenAI protocol to one endpoint, and the config decides whether that is the local Qwen or a cloud fallback. Swapping models is a config change. Qwen 2.5 1.5B runs locally because applicant financial data should not leave the host, and it is small enough to serve on CPU.

Around it: Compose for reproducible startup, Prometheus and Grafana for the golden signals, and a promptfoo gate. Two honest notes — Chroma is embedded rather than a service, and the CI workflow ships as a reference file you copy into .github/workflows; the local pre-push hook is the gate that actually runs today.

04

Speaker notes — about 90 seconds

Let me walk one real question through. The customer types it into Streamlit, which attaches a session ID so follow-up messages keep context, and an idempotency key so a retry cannot double-process.

Guardrails run before the model sees anything. That ordering is deliberate — an injection attempt is cheaper to stop at the boundary than to clean up afterwards. The same layer routes intent: casual chat does not need retrieval, an eligibility question does.

Retrieval detects that this is a personal loan and restricts the search to personal-loan clauses plus the general decision rules, so home-loan thresholds cannot contaminate the answer. Those clauses, the versioned system prompt and the recent conversation are assembled into the context. The call goes out through LiteLLM, which retries and can fall back if the local model is down.

Step eight is the part I am most pleased with. The model returns citations, and I do not trust them. Every Rule ID is looked up in Chroma, and anything that does not resolve to a real clause is discarded. The model cannot invent a citation, because an invented one never survives.

And look at the answer. Sixty thousand rupees clears the personal-loan income floor — but the policy also requires age, employment history and a CIBIL score, and it has none of those. Nothing has failed, so it cannot say no; nothing is confirmed, so it must not say yes. It returns NEEDS_INFORMATION and asks. That refusal to guess is the whole point of the project.

05

Speaker notes — about 75 seconds

Do not read this table out. Pick the four choices a reviewer will challenge.

Why RAG rather than fine-tuning? Because lending policy changes, and when it does I re-run ingestion — I do not retrain a model. Retrieval also gives me something fine-tuning cannot: the specific clause behind each answer, which is what makes the output auditable.

Why ChromaDB? The corpus is one policy document, so an embedded persistent index is the honest choice — no server to run. It keeps the same query interface a managed vector database would give me, so the migration path is open.

Why a local Qwen? Applicant income and credit data are exactly the kind of thing you do not send to a third-party API by default. A 1.5B instruct model is small enough to run on CPU and capable enough for constrained reasoning when the rules are supplied to it.

Why LiteLLM in front of it? So the application never knows which provider answered. My code makes one OpenAI-shaped call to one endpoint; the config decides the rest, and if the local container is down the request can fall back instead of failing.

One caveat worth owning: the commented Azure, Bedrock and Vertex entries in the LiteLLM config are examples, not configured deployments.

06

Speaker notes — about 60 seconds, then invite questions

To close: the left column is what actually runs. The pieces I would point to are grounded generation with verified citations, a local model so applicant data stays put, prompts treated as versioned artifacts rather than strings in code, guardrails on both sides of the model, and enough observability to know when it degrades.

The right column is explicitly future scope — none of it is built. The honest gaps are the ones I would fix first: there is no authentication yet, the CI workflow is supplied as a template rather than active, and evaluation covers a handful of assertions rather than a labelled quality set.

What I would emphasise to a production team is that the architecture already has the right seams. The vector store is embedded but speaks the interface a managed service would. The model sits behind a gateway, so swapping it is configuration. Prompts are released through an environment variable. None of the next steps require rewriting the application — they replace components behind interfaces that already exist.

And the boundary holds throughout: this is preliminary eligibility guidance, cited to policy, never an approval. Happy to take questions.
